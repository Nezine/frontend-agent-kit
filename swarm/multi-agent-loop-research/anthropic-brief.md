## 1. What Anthropic actually does

### 1.1 Workflows vs agents — the founding distinction (S1)

Anthropic groups everything under "agentic systems" and draws one architectural line:

- **Workflows** are systems where LLMs and tools are orchestrated through **predefined code paths**.
- **Agents** are systems where LLMs **dynamically direct their own processes and tool usage**, maintaining control over how they accomplish tasks.

Their standing advice: "find the simplest solution possible, and only increasing complexity when needed. This might mean not building agentic systems at all. Agentic systems often trade latency and cost for better task performance." Workflows give predictability and consistency for well-defined tasks; agents are the better option when flexibility and model-driven decision-making are needed at scale. Often, "optimizing single LLM calls with retrieval and in-context examples is usually enough."

Three core principles when implementing agents (S1, Summary):

1. Maintain **simplicity** in the agent's design.
2. Prioritize **transparency** by explicitly showing the agent's planning steps.
3. Carefully craft the **agent-computer interface (ACI)** through thorough tool documentation and testing — "think about how much effort goes into human-computer interfaces (HCI), and plan to invest just as much effort in creating good agent-computer interfaces."

On frameworks: frameworks "make it easy to get started by simplifying standard low-level tasks like calling LLMs, defining and parsing tools, and chaining calls together. However, they often create extra layers of abstraction that can obscure the underlying prompts and responses, making them harder to debug." Anthropic suggests starting with LLM APIs directly — "many patterns can be implemented in a few lines of code" — and, if a framework is used, understanding the underlying code.

### 1.2 The five workflow patterns (S1)

These are the composable building blocks. The foundational block underneath all of them is the **augmented LLM**: an LLM enhanced with retrieval, tools, and memory.

1. **Prompt chaining** — decompose a task into a sequence of steps, each LLM call processing the output of the previous one. Programmatic checks ("gates") can be added on intermediate steps "to ensure that the process is still on track." Best when the task decomposes cleanly into fixed subtasks; trades latency for accuracy.
2. **Routing** — classify an input and direct it to a specialized follow-up task. Best for complex tasks with distinct categories handled separately. Anthropic's own example: routing easy questions to smaller, cost-efficient models (Claude Haiku 4.5) and hard ones to more capable models (Claude Sonnet 4.5).
3. **Parallelization** — LLMs work simultaneously and outputs are aggregated programmatically. Two variations: **sectioning** (break into independent subtasks run in parallel) and **voting** (run the same task multiple times for diverse outputs). Sectioning example: one model instance processes user queries while another screens them for inappropriate content — "this tends to perform better than having the same LLM call handle both guardrails and the core response." Voting example: several prompts reviewing code for vulnerabilities.
4. **Orchestrator-workers** — a central LLM dynamically breaks down tasks, delegates to worker LLMs, and synthesizes results. Best for complex tasks where you can't predict the subtasks needed (e.g. coding, where the files to change depend on the task). Key difference from parallelization: subtasks aren't pre-defined; the orchestrator determines them from the input.
5. **Evaluator-optimizer** — one LLM call generates a response while another provides evaluation and feedback in a loop. Best when there are clear evaluation criteria and iterative refinement provides measurable value. The two signs of good fit: LLM responses demonstrably improve when a human articulates feedback, and the LLM can provide such feedback.

These patterns "aren't prescriptive… developers can shape and combine to fit different use cases. The key to success… is measuring performance and iterating on implementations… consider adding complexity only when it demonstrably improves outcomes."

### 1.3 Agents proper: the loop, ground truth, stopping conditions (S1)

Agents "begin their work with either a command from, or interactive discussion with, the human user. Once the task is clear, agents plan and operate independently, potentially returning to the human for further information or judgement. During execution, it's crucial for the agents to gain 'ground truth' from the environment at each step (such as tool call results or code execution) to assess its progress. Agents can then pause for human feedback at checkpoints or when encountering blockers. The task often terminates upon completion, but it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control."

"Agents are typically just LLMs using tools based on environmental feedback in a loop." Their autonomy means "higher costs, and the potential for compounding errors. We recommend extensive testing in sandboxed environments, along with the appropriate guardrails."

Why coding agents work especially well (S1, Appendix 1): code solutions are verifiable through automated tests; agents can iterate on solutions using test results as feedback; the problem space is well-defined and structured; output quality can be measured objectively. Anthropic's own implementation "can now solve real GitHub issues in the SWE-bench Verified benchmark based on the pull request description alone" — but "whereas automated testing helps verify functionality, human review remains crucial for ensuring solutions align with broader system requirements."

### 1.4 The multi-agent research system: orchestrator-worker at production scale (S2)

This is Anthropic's flagship published multi-agent system — the Research feature in Claude, built by a lead agent plus parallel subagents.

**Architecture:** "a multi-agent architecture with an orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel." The lead agent analyzes the query, develops a strategy, and spawns subagents to explore different aspects simultaneously. Subagents "act as intelligent filters by iteratively using search tools to gather information… and then returning a list of companies to the lead agent so it can compile a final answer."

**Why it works — compression, not just parallelism:** "The essence of search is compression: distilling insights from a vast corpus. Subagents facilitate compression by operating in parallel with their own context windows, exploring different aspects of the question simultaneously before condensing the most important tokens for the lead research agent. Each subagent also provides separation of concerns — distinct tools, prompts, and exploration trajectories — which reduces path dependency and enables thorough, independent investigations."

**Measured result:** "a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 subagents outperformed single-agent Claude Opus 4 by 90.2% on our internal research eval." The example given: identifying all board members of the companies in the Information Technology S&P 500 — the multi-agent system decomposed this into subagent tasks and found the answers, while the single agent "failed to find the answer with slow, sequential searches."

**Why the gain exists — token spend is the dominant factor:** "Multi-agent systems work mainly because they help spend enough tokens to solve the problem. In our analysis, three factors explained 95% of the performance variance in the BrowseComp evaluation… token usage by itself explains 80% of the variance, with the number of tool calls and the model choice as the two other explanatory factors." And: "upgrading to Claude Sonnet 4 is a larger performance gain than doubling the token budget on Claude Sonnet 3.7."

**The cost warning (same post, same section):** "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats. For economic viability, multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance." Also: "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today. For instance, most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time."

**When multi-agent excels (S2):** "valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools" — especially breadth-first queries pursuing multiple independent directions simultaneously.

**Prompt engineering — the primary lever (S2, 8 principles):**

1. **Think like your agents.** Anthropic built simulations "using our Console with the exact prompts and tools from our system, then watched agents work step-by-step. This immediately revealed failure modes: agents continuing when they already had sufficient results, using overly verbose search queries, or selecting incorrect tools."
2. **Teach the orchestrator how to delegate.** "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information." Early short instructions like "research the semiconductor shortage" were "vague enough that subagents misinterpreted the task or performed the exact same searches as other agents."
3. **Scale effort to query complexity.** Explicit scaling rules in the prompts: "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities." Early failure mode: "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources, and distracting each other with excessive updates."
4. **Tool design and selection are critical.** "Agent-tool interfaces are as critical as human-computer interfaces… an agent searching the web for context that only exists in Slack is doomed from the start." Heuristics given: examine all available tools first, match tool usage to user intent, prefer specialized tools over generic ones. "Bad tool descriptions can send agents down completely wrong paths, so each tool needs a distinct purpose and a clear description."
5. **Let agents improve themselves.** "We found that the Claude 4 models can be excellent prompt engineers. When given a prompt and a failure mode, they are able to diagnose why the agent is failing and suggest improvements." Anthropic built "a tool-testing agent — when given a flawed MCP tool, it attempts to use the tool and then rewrites the tool description to avoid failures. By testing the tool dozens of times, this agent found key nuances and bugs. This process for improving tool ergonomics resulted in a 40% decrease in task completion time for future agents using the new description."
6. **Start wide, then narrow down.** Agents "often default to overly long, specific queries that return few results." Prompt them to start with short, broad queries, evaluate what's available, then progressively narrow focus.
7. **Guide the thinking process.** Extended thinking "can serve as a controllable scratchpad. The lead agent uses thinking to plan its approach, assessing which tools fit the task, determining query complexity and subagent count, and defining each subagent's role… Subagents also plan, then use interleaved thinking after tool results to evaluate quality, identify gaps, and refine their next query."
8. **Parallel tool calling transforms speed and performance.** "The lead agent spins up 3-5 subagents in parallel rather than serially; the subagents use 3+ tools in parallel. These changes cut research time by up to 90% for complex queries."

Prompting strategy overall: "instilling good heuristics rather than rigid rules… frameworks for collaboration that define the division of labor, problem-solving approaches, and effort budgets," plus "explicit guardrails to prevent the agents from spiraling out of control" and "a fast iteration loop with observability and test cases."

**Evaluation of multi-agent systems (S2):**

- "Multi-agent systems don't work this way [following the same steps each time]. Even with identical starting points, agents might take completely different valid paths to reach their goal… we need flexible evaluation methods that judge whether agents achieved the right outcomes while also following a reasonable process."
- **Start evaluating immediately with small samples:** "We started with a set of about 20 queries representing real usage patterns… a prompt tweak might boost success rates from 30% to 80%. With effect sizes this large, you can spot changes with just a few test cases… it's best to start with small-scale testing right away with a few examples, rather than delaying until you can build more thorough evals."
- **LLM-as-judge scales when done well:** a rubric of factual accuracy, citation accuracy, completeness, source quality, and tool efficiency. "We experimented with multiple judges to evaluate each component, but found that a single LLM call with a single prompt outputting scores from 0.0-1.0 and a pass-fail grade was the most consistent and aligned with human judgements."
- **Human evaluation catches what automation misses:** human testers noticed early agents "consistently chose SEO-optimized content farms over authoritative but less highly-ranked sources like academic PDFs or personal blogs. Adding source quality heuristics to our prompts helped resolve this issue. Even in a world of automated evaluations, manual testing remains essential."
- **End-state evaluation for state-mutating agents (Appendix):** "Instead of judging whether the agent followed a specific process, evaluate whether it achieved the correct final state… For complex workflows, break evaluation into discrete checkpoints where specific state changes should have occurred, rather than attempting to validate every intermediate step."

**Production reliability (S2):**

- **Agents are stateful and errors compound.** "We can't just restart from the beginning: restarts are expensive and frustrating for users. Instead, we built systems that can resume from where the agent was when the errors occurred. We also use the model's intelligence to handle issues gracefully: for instance, letting the agent know when a tool is failing and letting it adapt works surprisingly well. We combine the adaptability of AI agents built on Claude with deterministic safeguards like retry logic and regular checkpoints."
- **Debugging needs tracing.** "Adding full production tracing let us diagnose why agents failed and fix issues systematically. Beyond standard observability, we monitor agent decision patterns and interaction structures — all without monitoring the contents of individual conversations, to maintain user privacy."
- **Deployment needs coordination.** Agents are "highly stateful webs of prompts, tools, and execution logic that run almost continuously… whenever we deploy updates, agents might be anywhere in their process… we use rainbow deployments to avoid disrupting running agents, by gradually shifting traffic from old to new versions while keeping both running simultaneously."
- **Synchronous execution creates bottlenecks.** "Currently, our lead agents execute subagents synchronously, waiting for each set of subagents to complete before proceeding. This simplifies coordination, but creates bottlenecks in the information flow… the lead agent can't steer subagents, subagents can't coordinate, and the entire system can be blocked while waiting for a single subagent to finish searching. Asynchronous execution would enable additional parallelism… But this asynchronicity adds challenges in result coordination, state consistency, and error propagation."
- **Subagent output to a filesystem to minimize the 'game of telephone' (Appendix):** "Rather than requiring subagents to communicate everything through the lead agent, implement artifact systems where specialized agents can create outputs that persist independently. Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator. This prevents information loss during multi-stage processing and reduces token overhead from copying large outputs through conversation history. The pattern works particularly well for structured outputs like code, reports, or data visualizations."
- **Long-horizon conversation management (Appendix):** "agents summarize completed work phases and store essential information in external memory before proceeding to new tasks. When context limits approach, agents can spawn fresh subagents with clean contexts while maintaining continuity through careful handoffs… retrieve stored context like the research plan from their memory rather than losing previous work when reaching the context limit."

### 1.5 The harness for long-running coding: planner–generator–evaluator (S3)

S3 (March 2026, Anthropic Labs) is the closest Anthropic post to our own loop — it is literally about making frontend design gradable and building complete apps autonomously. It is the single most transferable source in this brief.

**The GAN inspiration:** "Taking inspiration from Generative Adversarial Networks (GANs), I designed a multi-agent structure with a generator and an evaluator agent." The final architecture for full-stack coding was three agents: **planner, generator, evaluator**.

**Two failure modes of naive long-running agents:**

1. **Context loss / "context anxiety."** "Models tend to lose coherence on lengthy tasks as the context window fills… Some models also exhibit 'context anxiety,' in which they begin wrapping up work prematurely as they approach what they believe is their context limit. Context resets — clearing the context window entirely and starting a fresh agent, combined with a structured handoff that carries the previous agent's state and the next steps — addresses both these issues." This differs from compaction, where earlier parts are summarized in place: "compaction preserves continuity, it doesn't give the agent a clean slate, which means context anxiety can still persist." Note the model-dependence: "Claude Sonnet 4.5 exhibited context anxiety strongly enough that compaction alone wasn't sufficient… Opus 4.5 largely removed that behavior on its own, so I was able to drop context resets from this harness entirely. The agents were run as one continuous session across the whole build, with the Claude Agent SDK's automatic compaction handling context growth."
2. **Self-evaluation leniency.** "When asked to evaluate work they've produced, agents tend to respond by confidently praising the work — even when, to a human observer, the quality is obviously mediocre. This problem is particularly pronounced for subjective tasks like design, where there is no binary check equivalent to a verifiable software test." Key finding: "Separating the agent doing the work from the agent judging it proves to be a strong lever… the evaluator is still an LLM that is inclined to be generous towards LLM-generated outputs. But tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work, and once that external feedback exists, the generator has something concrete to iterate against."

**Making subjective quality gradable (frontend design loop):** Four grading criteria, given to both generator and evaluator in their prompts:

- **Design quality:** does the design feel like a coherent whole rather than a collection of parts? Colors, typography, layout, imagery combine into a distinct mood and identity.
- **Originality:** evidence of custom decisions, or template layouts, library defaults, and AI-generated patterns? "Unmodified stock components — or telltale signs of AI generation like purple gradients over white cards — fail here."
- **Craft:** typography hierarchy, spacing consistency, color harmony, contrast ratios. A competence check; "most reasonable implementations do fine here by default."
- **Functionality:** can users understand what the interface does, find primary actions, and complete tasks without guessing?

"Design quality and originality" were weighted more heavily than craft and functionality, because Claude already scored well on the latter by default; the criteria "explicitly penalized highly generic 'AI slop' patterns, and by weighting design and originality more heavily it pushed the model toward more aesthetic risk-taking." The evaluator was calibrated "using few-shot examples with detailed score breakdowns. This ensured the evaluator's judgment aligned with my preferences, and reduced score drift across iterations."

**The loop mechanics:** "I built the loop on the Claude Agent SDK… A generator agent first created an HTML/CSS/JS frontend based on a user prompt. I gave the evaluator the Playwright MCP, which let it interact with the live page directly before scoring each criterion and writing a detailed critique. In practice, the evaluator would navigate the page on its own, screenshotting and carefully studying the implementation before producing its assessment. That feedback flowed back to the generator as input for the next iteration. I ran 5 to 15 iterations per generation… Full runs stretched up to four hours. I also instructed the generator to make a strategic decision after each evaluation: refine the current direction if scores were trending well, or pivot to an entirely different aesthetic if the approach wasn't working."

Results: "the evaluator's assessments improved over iterations before plateauing… Later implementations tended to be better as a whole, but I regularly saw cases where I preferred a middle iteration over the last one." And: "Even on the first iteration, outputs were noticeably better than a baseline with no prompting at all, suggesting the criteria and associated language themselves steered the model away from generic defaults before any evaluator feedback led to further refinement." In one run, iteration 9 produced a polished but expected dark museum landing page; iteration 10 "scrapped the approach entirely and reimagined the site as a spatial experience: a 3D room with a checkered floor rendered in CSS perspective, artwork hung on the walls in free-form positions, and doorway-based navigation."

**The three-agent full-stack architecture:**

- **Planner:** "took a simple 1-4 sentence prompt and expanded it into a full product spec. I prompted it to be ambitious about scope and to stay focused on product context and high level technical design rather than detailed technical implementation… if the planner tried to specify granular technical details upfront and got something wrong, the errors in the spec would cascade into the downstream implementation. It seemed smarter to constrain the agents on the deliverables to be produced and let them figure out the path as they worked. I also asked the planner to find opportunities to weave AI features into the product specs."
- **Generator:** "work in sprints, picking up one feature at a time from the spec. Each sprint implemented the app with a React, Vite, FastAPI, and SQLite (later PostgreSQL) stack, and the generator was instructed to self-evaluate its work at the end of each sprint before handing off to QA. It also had git for version control."
- **Evaluator:** "used the Playwright MCP to click through the running application the way a user would, testing UI features, API endpoints, and database states. It then graded each sprint against both the bugs it had found and a set of criteria modeled on the frontend experiment, adapted here to cover product depth, functionality, visual design, and code quality. Each criterion had a hard threshold, and if any one fell below it, the sprint failed and the generator got detailed feedback on what went wrong."

**The sprint contract (the most directly reusable mechanism):** "Before each sprint, the generator and evaluator negotiated a sprint contract: agreeing on what 'done' looked like for that chunk of work before any code was written… The generator proposed what it would build and how success would be verified, and the evaluator reviewed that proposal to make sure the generator was building the right thing. The two iterated until they agreed. Communication was handled via files: one agent would write a file, another agent would read it and respond either within that file or with a new file that the previous agent would read in turn."

**Measured comparison (retro game maker, Opus 4.5):** solo run — "20 min, $9" — produced a broken game (entities appeared but nothing responded to input; "the wiring between entity definitions and the game runtime was broken"). Full harness — "6 hr, $200" (over 20× more expensive) — planner expanded the prompt into "a 16-feature spec spread across ten sprints," and the result was playable with richer editors and working play mode. "The harness was over 20x more expensive, but the difference in output quality was immediately apparent."

**Getting the evaluator to perform took work:** "Out of the box, Claude is a poor QA agent. In early runs, I watched it identify legitimate issues, then talk itself into deciding they weren't a big deal and approve the work anyway. It also tended to test superficially, rather than probing edge cases… The tuning loop was to read the evaluator's logs, find examples where its judgment diverged from mine, and update the QA's prompt to solve for those issues. It took several rounds of this development loop before the evaluator was grading in a way that I found reasonable."

**Iterating on the harness itself — simplify by ablation, one component at a time:** "Every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing, both because they may be incorrect, and because they can quickly go stale as models improve." First attempt — cutting the harness back radically — failed to replicate performance and "it also became difficult to tell which pieces of the harness design were actually load-bearing." So: "I moved to a more methodical approach, removing one component at a time and reviewing what impact it had on the final result." With Opus 4.6, the sprint construct was removed (the model could handle the job without decomposition), the evaluator moved to a single pass at the end, and the run still took "about 4 hours and $124 in token costs" for a DAW build — but the QA agent still caught real gaps ("clips can't be dragged/moved on the timeline… audio recording is still stub-only"). "The practical implication is that the evaluator is not a fixed yes-or-no decision. It is worth the cost when the task sits beyond what the current model does reliably solo." Final lesson: "When working on more complex tasks, there is sometimes headroom from decomposing the task and applying specialized agents to each aspect of the problem. And when a new model lands, it is generally good practice to re-examine a harness, stripping away pieces that are no longer load-bearing."

### 1.6 Effective harnesses: initializer + coding agent, files as memory (S4)

S4 is the earlier harness post S3 builds on. The core problem: "getting agents to make consistent progress across multiple context windows remains an open problem… each new session begins with no memory of what came before. Imagine a software project staffed by engineers working in shifts, where each new engineer arrives with no memory of what happened on the previous shift."

Two observed failure modes (Opus 4.5 on the Claude Agent SDK, given only a high-level prompt):

1. The agent "tended to try to do too much at once — essentially to attempt to one-shot the app… running out of context in the middle of its implementation, leaving the next session to start with a feature half-implemented and undocumented."
2. "After some features had already been built, a later agent instance would look around, see that progress had been made, and declare the job done."

**The two-part solution:**

1. **Initializer agent** (first session only): sets up the environment — an `init.sh` script, a `claude-progress.txt` file logging what agents have done, and an initial git commit.
2. **Coding agent** (every subsequent session): makes incremental progress, then leaves structured updates.

**Feature list as a deterministic gate:** the initializer writes "a comprehensive file of feature requirements expanding on the user's initial prompt" — in the claude.ai-clone example, "over 200 features, such as 'a user can open a new chat, type in a query, press enter, and see an AI response.' These features were all initially marked as 'failing'." Coding agents edit the file "only by changing the status of a passes field," with strongly-worded instructions like "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." JSON was chosen over Markdown because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files."

**Incremental progress:** the coding agent works on "only one feature at a time," then commits progress to git with descriptive messages and writes summaries in the progress file — "this allowed the model to use git to revert bad code changes and recover working states."

**Testing as a human would:** "Absent explicit prompting, Claude tended to make code changes, and even do testing with unit tests or curl commands against a development server, but would fail to recognize that the feature didn't work end-to-end… Claude mostly did well at verifying features end-to-end once explicitly prompted to use browser automation tools and do all testing as a human user would. Providing Claude with these kinds of testing tools dramatically improved performance, as the agent was able to identify and fix bugs that weren't obvious from the code alone." (Limitation noted: Claude "can't see browser-native alert modals through the Puppeteer MCP, and features relying on these modals tended to be buggier.")

**Getting-up-to-speed routine (every session):** run `pwd`; read git logs and progress files; read the features list and choose the highest-priority feature not yet done; run `init.sh` to start the dev server and run a basic end-to-end test *before* implementing a new feature — "this ensured that Claude could quickly identify if the app had been left in a broken state, and immediately fix any existing bugs. If the agent had instead started implementing a new feature, it would likely make the problem worse."

**Open question (S4, Future work):** "it's still unclear whether a single, general-purpose coding agent performs best across contexts, or if better performance can be achieved through a multi-agent architecture. It seems reasonable that specialized agents like a testing agent, a quality assurance agent, or a code cleanup agent, could do an even better job at sub-tasks." S3 (2026-03) is, in effect, the answer to that open question: the three-agent planner–generator–evaluator.

### 1.7 Context engineering: context is a finite resource (S5)

"Context engineering refers to the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference, including all the other information that may land there outside of the prompts." The guiding principle: "find the smallest set of high-signal tokens that maximize the likelihood of your desired outcome."

- **Context rot:** "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases… Context, therefore, must be treated as a finite resource with diminishing marginal returns… Every new token introduced depletes this budget by some amount."
- **System prompts at the right altitude:** "the Goldilocks zone between two common failure modes… hardcoding complex, brittle logic… [vs] vague, high-level guidance that fails to give the LLM concrete signals." Organize prompts into sections with XML tags or Markdown headers; "striving for the minimal set of information that fully outlines your expected behavior. (Note that minimal does not necessarily mean short…)" Start minimal with the best model, then add instructions based on failure modes found in testing.
- **Tools:** "self-contained, robust to error, and extremely clear with respect to their intended use… One of the most common failure modes we see is bloated tool sets that cover too much functionality or lead to ambiguous decision points about which tool to use. If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better."
- **Examples:** don't stuff "a laundry list of edge cases" into the prompt; "curate a set of diverse, canonical examples that effectively portray the expected behavior… examples are the 'pictures' worth a thousand words."
- **Just-in-time retrieval over upfront loading:** "agents built with the 'just in time' approach maintain lightweight identifiers (file paths, stored queries, web links, etc.) and use these references to dynamically load data into context at runtime using tools… This approach mirrors human cognition: we generally don't memorize entire corpuses of information, but rather introduce external organization and indexing systems like file systems, inboxes, and bookmarks to retrieve relevant information on demand." Claude Code's hybrid: CLAUDE.md files dropped in up front, while glob/grep retrieve files just-in-time.
- **Three long-horizon techniques:** (a) **Compaction** — summarize a near-full conversation and reinitiate with the summary; in Claude Code the model "preserves architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs," then continues "with this compressed context plus the five most recently accessed files." Tune the compaction prompt for recall first, then precision; "one of the safest lightest touch forms of compaction is tool result clearing." (b) **Structured note-taking / agentic memory** — "the agent regularly writes notes persisted to memory outside of the context window. These notes get pulled back into the context window at later times." Example: Claude playing Pokémon maintaining "precise tallies across thousands of game steps… maps of explored regions… strategic notes of combat strategies." (c) **Sub-agent architectures** — "specialized sub-agents can handle focused tasks with clean context windows. The main agent coordinates with a high-level plan while subagents perform deep technical work… Each subagent might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)." Choice depends on task: compaction for conversational flow, note-taking for iterative development with clear milestones, multi-agent for complex research where parallel exploration pays.
- "As models become more capable, the challenge isn't just crafting the perfect prompt — it's thoughtfully curating what information enters the model's limited attention budget at each step… smarter models require less prescriptive engineering, allowing agents to operate with more autonomy. But even as capabilities scale, treating context as a precious, finite resource will remain central."

### 1.8 Writing tools for agents (S7 — read in part, lines 0–210)

Tools are "a new kind of software which reflects a contract between deterministic systems and non-deterministic agents… an agent might hallucinate or even fail to grasp how to use a tool." The goal: "increase the surface area over which agents can be effective."

**Method — prototype, evaluate, collaborate:**

- Start with a quick prototype; give Claude documentation for the libraries/APIs the tools rely on; wrap tools in a local MCP server to test in Claude Code; "test the tools yourself to identify any rough edges."
- **Run an evaluation:** generate lots of evaluation tasks "grounded in real world uses… based on realistic data sources… avoid overly simplistic or superficial 'sandbox' environments that don't stress-test your tools." Strong tasks require multiple tool calls, "potentially dozens." Each prompt is paired with a verifiable response or outcome; verifiers can be "as simple as an exact string comparison… or as advanced as enlisting Claude to judge the response. Avoid overly strict verifiers that reject correct responses due to spurious differences." Optionally specify expected tools per task — but "because there might be multiple valid paths to solving tasks correctly, try to avoid overspecifying or overfitting to strategies."
- Run evals programmatically with "simple agentic loops (while-loops wrapping alternating LLM API and tool calls): one loop for each evaluation task." Instruct eval agents to output reasoning and feedback blocks *before* tool-call blocks ("may increase LLMs' effective intelligence by triggering chain-of-thought behaviors"); interleaved thinking gives similar functionality off the shelf. Collect metrics beyond accuracy: "total runtime of individual tool calls and tasks, the total number of tool calls, the total token consumption, and tool errors."
- **Analyze results with agents:** "Agents are your helpful partners in spotting issues… However, keep in mind that what agents omit in their feedback and responses can often be more important than what they include. LLMs don't always say what they mean. Observe where your agents get stumped or confused. Read through your evaluation agents' reasoning and feedback (or CoT)… Review the raw transcripts (including tool calls and tool responses) to catch any behavior not explicitly described in an agent's CoT." Example: Claude "was needlessly appending `2025` to the [web search] tool's `query` parameter, biasing search results" — fixed by improving the tool description.
- **Let agents improve the tools:** "concatenate the transcripts from your evaluation agents and paste them into Claude Code. Claude is an expert at analyzing transcripts and refactoring lots of tools all at once." Anthropic relied on held-out test sets "to ensure we did not overfit to our 'training' evaluations" and found improvements "even beyond what we achieved with 'expert' tool implementations — whether those tools were manually written by our researchers or generated by Claude itself."
- *(Remainder of S7, lines 210–293 — returning meaningful context, optimizing tool responses for token efficiency, prompt-engineering tool descriptions — **CHƯA ĐỌC**.)*

**Principles (from the portion read):**

- **Choose the right tools (and don't build the wrong ones):** "More tools don't always lead to better outcomes. A common error… is tools that merely wrap existing software functionality or API endpoints — whether or not the tools are appropriate for agents." Agents have limited context while computer memory is cheap: a `list_contacts` tool that returns ALL contacts wastes the agent's limited context; a `search_contacts` tool is the agent-native choice. "Build a few thoughtful tools targeting specific high-impact workflows, which match your evaluation tasks and scaling up from there." Tools can consolidate functionality: "Instead of implementing a `list_users`, `list_events`, and `create_event` tools, consider implementing a `schedule_event` tool which finds availability and schedules an event." "Make sure each tool you build has a clear, distinct purpose… Too many tools or overlapping tools can also distract agents from pursuing efficient strategies."
- **Namespacing:** "When tools overlap in function or have a vague purpose, agents can get confused about which ones to use. Namespacing (grouping related tools under common prefixes) can help delineate boundaries… namespacing tools by service (e.g. `asana_search`, `jira_search`) and by resource (e.g. `asana_projects_search`, `asana_users_search`)… We have found selecting between prefix- and suffix-based namespacing to have non-trivial effects on our tool-use evaluations."

### 1.9 Claude Code subagents and the Agent SDK (S6 read in full; S8 read in part)

**What a subagent is (S8):** "specialized AI assistants that handle specific types of tasks. Use one when a side task would flood your main conversation with search results, logs, or file contents you won't reference again: the subagent does that work in its own context and returns only the summary. Define a custom subagent when you keep spawning the same kind of worker with the same instructions. Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions."

**What subagents buy (S8/S6):** preserve context (exploration stays out of the main conversation); enforce constraints (limit tools); reuse configurations across projects; specialize behavior with focused prompts; control costs by routing tasks to faster, lower-cost models like Haiku. In the SDK (S6): context isolation, parallelization ("multiple subagents can run concurrently, so independent subtasks finish in the time of the slowest one rather than the sum of all of them"), specialized instructions, tool restrictions ("a `doc-reviewer` subagent might only have access to Read and Grep tools, ensuring it can analyze but never accidentally modify your documentation files").

**Built-in subagents (S8):** Explore (fast, read-only codebase search; Write and Edit denied; thoroughness quick/medium/very thorough; a user/project subagent named `Explore` overrides the built-in, e.g. with `model: haiku`); Plan (read-only research during plan mode); General-purpose (every tool available to subagents; complex multi-step tasks). Explore and Plan "start without your CLAUDE.md files and the git status snapshot to keep research fast and inexpensive." Built-ins can be restricted via `permissions.deny`; denying the `Agent` tool blocks all delegation.

**Definition format (S8):** a Markdown file with YAML frontmatter (the configuration) plus a Markdown body (the system prompt), stored in `.claude/agents/` (project, checked into version control) or `~/.claude/agents/` (user-level, all projects). Frontmatter fields include `description`, `tools`, `disallowedTools`, `model`, `permissionMode`, `mcpServers`, `hooks`, `maxTurns`, `autoCompactWindow`, `skills`, `initialPrompt`, `memory`, `effort`, `background`, `omitClaudeMd`, `isolation` (including `isolation: worktree`, which gives the subagent an isolated copy of the repository). "Subagents receive only this system prompt plus basic environment details like the working directory, not the Claude Code system prompt." Descriptions must be short and clear — they are how Claude decides when to delegate, and "when the combined descriptions of your subagents, except the built-in ones, exceed 15,000 tokens, Claude Code shows a warning at startup."

**SDK mechanics (S6):**

- Three ways to create subagents: programmatically via the `agents` parameter in `query()` options (recommended for SDK apps), filesystem-based `.claude/agents/` Markdown files, or the built-in `general-purpose` subagent via the Agent tool. Programmatic definitions take precedence over filesystem ones with the same name.
- **What a subagent inherits:** "Unless the subagent is a fork, its context window starts fresh, with no parent conversation… The only content you pass from parent to subagent is the Agent tool's prompt string, so include any file paths, error messages, or decisions the subagent needs directly in that prompt." It receives its own system prompt, the Agent tool's prompt, project CLAUDE.md (unless `omitClaudeMd`), and tool definitions; it does NOT receive the parent's conversation history, tool results, preloaded skill content (unless listed), or the parent's system prompt. "An API error that ends the subagent early, such as a rate limit, is never delivered as its result."
- **Forks:** a fork "copies the conversation so far instead of starting fresh" (available from Claude Code v2.1.302 via `subagent_type: "fork"`).
- **Background by default:** "By default, a subagent your main agent spawns runs in the background. The Agent tool result has `status: "async_launched"`, and the report arrives in a later turn. Claude waits when its next action needs the report: the call blocks and returns `status: "completed"`." You can force waiting in the prompt ("run the test-runner agent and wait for it") or set `background: true` in the definition.
- **Resume:** a subagent can be resumed to continue where it left off; when it stops at its `maxTurns` limit, "Claude Code returns its output marked as partial, and you can resume the agent to continue." A completed subagent's Agent tool result includes `agentId`; Explore and Plan are one-shot and don't return one.
- **Hard caps (the deterministic guardrails):** depth `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (default **3 layers** below the main agent; `1` stops subagents from spawning their own); concurrency `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (default **20** running at once; further spawns are refused with `Concurrent subagent limit reached`); spend `maxBudgetUsd` / `max_budget_usd` (no default limit; enforces by refusing more spawns, stopping background subagents, and ending the query with `error_max_budget_usd`). "Claude decides on its own when to spawn a subagent and how many to spawn… a subagent can spawn subagents of its own, so one prompt can grow into a tree of agents. You can cap that growth in three ways." Opus 5 "delegates to subagents more readily than earlier models, so the depth, concurrency, and spend limits matter most on queries that run Opus 5" — and prompt steering alone is not enough: "Either instruction only steers Claude, so set the limits as well. Claude Code enforces them however Claude decides to delegate."
- **Scale-up path:** "Subagents work well for a few delegated tasks per turn. For runs that coordinate dozens to hundreds of agents, use the `Workflow` tool, which moves the orchestration into a script the runtime executes outside the conversation context." (TypeScript Agent SDK v0.3.149+; include `Workflow` in `allowedTools` to auto-approve workflow runs.)
- **Troubleshooting note with direct relevance to our probe-4 failure:** the SDK docs treat "API errors in subagents" and partial/maxTurns output as normal, resumable states — never as a signal to silently end the run.

## 2. What transfers to our loop — and how

Our loop is, in Anthropic's vocabulary, a **prompt-chaining workflow with an evaluator-optimizer loop and deterministic gates** — not a free-running agent swarm. That is a strength: S1 says workflows are the right default, and S3's three-agent harness is the closest published precedent. Transfers, ranked by value per hour of sprint time:

### T1. The generator–evaluator separation is load-bearing — keep it, and make the evaluator skeptical (S3, S1)

- **What:** never let the builder grade its own work. S3: "tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work." Our loop already does this (independent grading). Keep the roles in **separate agents/sessions with separate prompts**; do not merge builder + grader into one agent to save time.
- **How in our sprint:** the grader agent gets its own system prompt that explicitly instructs skepticism ("identify legitimate issues, then talk itself into deciding they weren't a big deal and approve the work anyway" is the documented failure mode — forbid it: every score below threshold must name the concrete defect). Give the grader the four S3 criteria adapted to mobile: design quality, originality, craft, functionality — with **design quality and originality weighted more heavily**, because S3 found craft/functionality are already handled well by default, while generic "AI slop" is the real risk. Our taste lock already encodes this; translate the taste lock into the grader's rubric verbatim so builder and grader share the same criteria (S3 gave the same four criteria to both agents).
- **Calibrate the grader with few-shot examples** (S3): "few-shot examples with detailed score breakdowns… ensured the evaluator's judgment aligned with my preferences, and reduced score drift across iterations." In practice: before the sprint, feed the grader 2–3 scored examples (a good screen, a slop screen, a broken screen) with the score each should receive and why. This is the cheapest calibration step we have and Anthropic needed "several rounds" of it before the evaluator graded reasonably — so do it *before* the sprint, not during.

### T2. The sprint contract: agree on "done" before building (S3)

- **What:** "Before each sprint, the generator and evaluator negotiated a sprint contract: agreeing on what 'done' looked like for that chunk of work before any code was written… The generator proposed what it would build and how success would be verified, and the evaluator reviewed that proposal."
- **How in our sprint:** our "taste lock before HTML" step *is* a sprint contract. Strengthen it: the contract should be a short written file (not chat) listing (a) the screens/features, (b) the exact observable check for each ("button X navigates to screen Y", "list renders ≥ N items from Convex"), (c) the gate thresholds (taste score, no crashes, no stubs). The builder proposes it, the grader (or coordinator) approves it, and the gate checks *the contract*, not the builder's claims. This directly prevents the S4 failure mode where an agent "look[s] around, see[s] that progress had been made, and declare[s] the job done."

### T3. Gate first, and make the gate deterministic where possible (S1, S2, S4)

- **What:** S1's prompt chaining explicitly allows "programmatic checks ('gates') on any intermediate steps to ensure that the process is still on track." S2: judge outcomes, not paths — "evaluate whether it achieved the correct final state… break evaluation into discrete checkpoints where specific state changes should have occurred." S4: a JSON feature list, all initially "failing", edited only by flipping a `passes` field, with "it is unacceptable to remove or edit tests" as a strongly-worded instruction.
- **How in our sprint:** our "gate first" step already matches. Concretely: keep a machine-checkable gate file (JSON, not Markdown — S4: "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files") listing every required behavior as pass/fail; the gate agent may only flip flags, never rewrite the list; a failing gate blocks the next round. Add the S4 rule verbatim to the builder prompt: never delete or weaken a failing test/check to make it pass. And run the gate **before** any new feature work in each round — S4's get-up-to-speed routine runs the end-to-end test first so a broken state is fixed before new work makes it worse.

### T4. Files as the handoff, not conversation history (S2 Appendix, S4, S5)

- **What:** "Subagent output to a filesystem to minimize the 'game of telephone'… Subagents call tools to store their work in external systems, then pass lightweight references back to the coordinator. This prevents information loss during multi-stage processing and reduces token overhead." S4: `claude-progress.txt` + git history is how a fresh-context agent gets up to speed. S5: structured note-taking — "the agent regularly writes notes persisted to memory outside of the context window."
- **How in our sprint:** every agent writes its output to a file (taste lock file, gate JSON, grade report, fix list) and passes only a short reference + summary to the coordinator. This is also the direct mitigation for our probe-4 yield death: if an agent dies mid-loop, the *files* are the resume point, not the dead session. A fresh agent reads the progress file + git log + gate JSON and continues — exactly S4's routine. Never rely on a single long-lived session holding all state in conversation.

### T5. Scale effort to complexity — explicit budgets in the prompt (S2)

- **What:** S2's scaling rules ("simple fact-finding: 1 agent, 3–10 tool calls; direct comparisons: 2–4 subagents, 10–15 calls each; complex research: 10+ subagents") exist because "agents struggle to judge appropriate effort" and the early failure was "spawning 50 subagents for simple queries."
- **How in our sprint:** our "fix top 2, stop at 3 rounds" *is* an effort budget — keep it, and write it as explicit numbers in every agent prompt (max rounds, max fixes per round, stop condition), not as a vague "iterate until good." S1: agents need "stopping conditions (such as a maximum number of iterations) to maintain control." Also adopt S6's hard-cap pattern at the harness level: a depth/concurrency/spend cap enforced by the coordinator script, not by asking the model nicely (S6: "Either instruction only steers Claude, so set the limits as well").

### T6. Start wide, then narrow; start with the criteria, not the feedback (S2, S3)

- **What:** S2 principle 6 (broad queries first, then narrow). S3: "Even on the first iteration, outputs were noticeably better than a baseline with no prompting at all, suggesting the criteria and associated language themselves steered the model away from generic defaults before any evaluator feedback."
- **How in our sprint:** the taste lock *is* the "criteria first" step — invest in it, because S3 shows the criteria alone do much of the work before any loop runs. In the build round, have the builder first produce the broad structure (all screens, navigation), then refine — not polish one screen to perfection while others are stubs.

### T7. Evaluate outcomes with a rubric + a human check; keep a small eval set (S2)

- **What:** S2's LLM-as-judge: "a single LLM call with a single prompt outputting scores from 0.0-1.0 and a pass-fail grade was the most consistent and aligned with human judgements" — rubric: factual accuracy, citation accuracy, completeness, source quality, tool efficiency. Adapted to us: correctness (does it work), completeness (all contract items), design quality, originality, craft. And: "Human evaluation catches what automation misses… manual testing remains essential." Start with ~20 test cases (S2) — for us, ~20 tap-through checks on the real phone.
- **How in our sprint:** the independent grader outputs 0.0–1.0 per criterion + pass/fail (matches our gate), and a human does the final phone tap-through before submission. The demo-on-real-phone requirement (40 points) *is* the human evaluation step — treat it as part of the loop, not as an afterthought.

### T8. Let agents improve the harness — but between sprints, not during (S2 principle 5, S3, S7)

- **What:** S2: "When given a prompt and a failure mode, [Claude 4 models] are able to diagnose why the agent is failing and suggest improvements" — and the tool-testing agent cut task completion time 40% by rewriting tool descriptions after dozens of test runs. S7: paste eval transcripts into Claude Code and let it refactor the tools; use held-out test sets to avoid overfitting. S3: simplify the harness by removing one component at a time and measuring the impact — never by radical cuts, because then "it also became difficult to tell which pieces… were actually load-bearing."
- **How in our sprint:** after the hackathon (or between practice runs), run a post-mortem pass: give the failing transcripts + gate results to an agent and ask it to propose *one* prompt/harness change, then test that change on a held-out task. Do NOT let an agent rewrite its own prompts mid-sprint — that is a recipe for the runaway behavior S2 warns about ("small changes to the lead agent can unpredictably change how subagents behave"). One change at a time, measured.

### T9. Tool design: few, distinct, well-described tools; prefer search over list (S1 ACI, S5, S7)

- **What:** the ACI deserves as much effort as HCI (S1). Tools must be self-contained, robust to error, extremely clear on intended use, with minimal overlap (S5). Prefer `search_*` over `list_*` to save context (S7). Namespace by service/resource (S7). Test tools by watching the agent use them (S2 principle 1: "think like your agents" — build simulations with the exact prompts and tools, then watch step-by-step).
- **How in our sprint:** our agents' "tools" are mostly file writes, shell commands, and screenshots. Keep the tool surface small and named distinctly (e.g. `write_gate_json` vs `write_grade_report`, not a generic `write_file` used for everything with ambiguous intent). In prompts, give each tool a one-line purpose + an example, the way S1 recommends writing "a great docstring for a junior developer."

### T10. Context hygiene: smallest high-signal set; subagent summaries are 1,000–2,000 tokens (S5, S6, S8)

- **What:** context rot is real; every token depletes the attention budget (S5). Subagents return "only a condensed, distilled summary of its work (often 1,000-2,000 tokens)" (S5); in the SDK, "only its final message returns to the parent" (S6).
- **How in our sprint:** cap what each worker returns to the coordinator (summary + file paths, not full logs/screenshots dumps). The coordinator holds the plan + gate JSON; workers hold the detail. This is the architectural reason our 4-assistant fleet should communicate through files + short messages, not by forwarding whole transcripts.

## 3. What does NOT transfer — and why

### N1. The 90.2% multi-agent gain does not transfer to our coding sprint

S2's headline number (+90.2% over single-agent Opus 4) is for **open-ended, breadth-first research** with a strong lead + weaker subagents. The same post explicitly says the pattern is a poor fit where "all agents need to share the same context or involve many dependencies between agents" and that "most coding tasks involve fewer truly parallelizable tasks than research." Our sprint is a single coherent mobile app — screens, navigation, and data layer are deeply interdependent, not parallelizable research threads. Do not cite 90.2% as justification for adding more agents to the build. The transferable part is the *orchestrator-worker shape with compression*, not the number.

### N2. The token economics are inverted for us — Anthropic spends 15×, we spend $0.00

S2: multi-agent uses ~15× the tokens of chat, single agents ~4×. S3: the full harness cost $200 vs $9 solo (20×+) for the game maker; $124 for the DAW run. Anthropic's conclusion: "multi-agent systems require tasks where the value of the task is high enough to pay for the increased performance." Our budget is $0.00 on free tiers (Gemini free, Groq fallback). We cannot buy our way out of quality problems with more tokens or more agents. Every additional agent/round must be justified against the free-tier rate limits, not against Anthropic's paid-token logic. The correct inference is the opposite of "add agents": keep the fleet small (our 4 assistants, sequential handoffs, 3-round cap) and spend the scarce budget on the *evaluator* and the *gate*, where S3 shows the lift per token is highest.

### N3. Anthropic's long runs (4–6 hours, multi-day) do not fit a 5-hour sprint

S3's frontend runs "stretched up to four hours" with 5–15 iterations; the full-stack harness ran 6 hours. S4's harness spans "hours, or even days" across many context windows. Our sprint is 5 hours total including demo prep, with a 3-round cap. Transfers that assume long horizons — context resets across sessions, multi-day initializer/coding-agent rhythms, rainbow deployments — must be compressed: our "context reset" is simply starting a fresh agent that reads the progress file (T4), and our iteration budget is 3, not 5–15. Do not copy the iteration counts; copy the *structure* (contract → build → independent eval → fix top 2 → stop).

### N4. Agent Teams (peer-to-peer multi-agent) are experimental and not our model — CHƯA ĐỌC, do not adopt

Anthropic's "agent teams" (multiple full Claude sessions messaging each other, per the subagent docs' cross-references) are experimental, require an opt-in flag, and are designed for long, loosely-coupled work. Our fleet is coordinator-driven with deterministic gates — the opposite topology. Peer-to-peer agent messaging would remove the deterministic control our gate loop depends on, and S2 warns that "small changes to the lead agent can unpredictably change how subagents behave" and that multi-agent systems have "emergent behaviors, which arise without specific programming." Keep the coordinator as the single point of control; workers do not message each other. (Agent Teams docs themselves are **CHƯA ĐỌC** — this is a design judgment from S1/S2/S6, not a claim about the Teams docs' contents.)

### N5. The Claude Agent SDK / Claude Code subagent machinery does not transfer literally

S6/S8 describe `query()`, `AgentDefinition`, `maxTurns`, `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, forks, background subagents, and the `Workflow` tool — all inside Anthropic's own runtime. Our fleet runs on a different stack (Muse agents, Gemini/Groq models, Expo/Convex/Supabase) with no Agent SDK. What transfers is the *interface design* (own context window, own system prompt, restricted tools, summary-only return, hard caps enforced by the harness — T5/T10), not the API. Do not propose "use the Agent SDK" for the hackathon; it would require Claude API keys, paid usage, and a rewrite of the harness the night before the sprint.

### N6. "Let agents improve themselves" must not become self-modifying prompts mid-sprint

S2 principle 5 and S7 both endorse agents diagnosing failures and rewriting prompts/tools — but always *offline*, with held-out test sets and human review of the change. During a live 5-hour sprint, an agent rewriting its own gate criteria or another agent's prompt is an uncontrolled change to the deterministic loop (and S2's warning applies: "minor changes cascade into large behavioral changes"). Freeze prompts and gate criteria at sprint start; improvement happens between runs (T8).

### N7. Anthropic's "human in the loop" assumes a human who can intervene — our sprint has 4 agents and 1 human

S1/S2 assume agents "pause for human feedback at checkpoints or when encountering blockers" and that "manual testing remains essential." In our sprint the human owner is also the demo presenter and cannot babysit four agents. So the "human checkpoint" must be *designed into* the loop as the gate + phone tap-through (T7), not assumed as continuous supervision. If an agent blocks, the harness rule should be: write the blocker to the progress file and stop that round cleanly — never spin in a retry loop (our probe-4 yield death is the local version of S2's "agents continuing when they already had sufficient results" / spiraling failure mode).

### N8. GUARD/security training: Anthropic's posts do not cover it

None of the sources read in this brief address prompt-injection defense, GUARD training, or adversarial robustness of a multi-agent harness (S2 mentions "explicit guardrails to prevent the agents from spiraling out of control" only as effort/spend guardrails, not security). Our known gap — "GUARD/security training is NOT ship-ready (pilot only)" — gets **no transferable pattern from Anthropic's published engineering posts read here**. Do not claim Anthropic endorses any specific guard design. The closest transferable items are deterministic: tool restrictions per subagent (S6/S8), permission modes, and hard spend/depth caps (S6) — all *harness-enforced*, never prompt-only (S6: "Either instruction only steers Claude, so set the limits as well").

**Anthropic làm gì (đã đọc kỹ 6 nguồn chính ngày 2026-11-13):**

- Phân biệt **workflow** (đường đi cố định do code định sẵn) với **agent** (LLM tự quyết định bước tiếp theo). Khuyên dùng giải pháp đơn giản nhất trước, chỉ thêm phức tạp khi chứng minh được hiệu quả. Năm mẫu workflow: chaining (nối bước), routing (phân loại), parallelization (chạy song song), orchestrator-workers (điều phối viên chia việc), evaluator-optimizer (một agent làm, một agent chấm rồi lặp lại).
- Hệ thống nghiên cứu đa agent (lead Opus 4 + subagent Sonnet 4) hơn agent đơn **90,2%** trên eval nội bộ — nhưng tốn **~15 lần token** so với chat thường, nên chỉ đáng khi nhiệm vụ đủ giá trị. Bí quyết là **nén thông tin**: mỗi subagent có context riêng, chỉ trả về tóm tắt cho lead. Quy tắc prompt quan trọng: dạy lead cách giao việc chi tiết (mục tiêu + định dạng output + ranh giới), ấn định effort theo độ khó (không spawn 50 subagent cho câu hỏi đơn giản), bắt đầu rộng rồi hẹp dần, chạy song song 3–5 subagent.
- Harness cho coding dài hơi: **planner – generator – evaluator** (lấy cảm hứng từ GAN). Lỗi lớn nhất của agent tự chấm mình là luôn khen bài của mình; tách evaluator riêng và bắt nó hoài nghi thì hiệu quả hơn nhiều. Bốn tiêu chí chấm design: chất lượng tổng thể, tính độc đáo, kỹ thuật (craft), chức năng — trong đó **độc đáo và chất lượng tổng thể được ưu tiên** vì agent mặc định đã làm tốt craft/chức năng nhưng hay ra "AI slop" (ví dụ gradient tím trên card trắng). Trước mỗi sprint, generator và evaluator **thương lượng "sprint contract"** — thống nhất "done" nghĩa là gì trước khi viết code. So sánh thực tế: chạy solo 20 phút/$9 ra game hỏng; chạy full harness 6 giờ/$200 ra game chơi được.
- Harness bền vững qua nhiều session: dùng file làm bộ nhớ — `claude-progress.txt`, danh sách feature dạng **JSON** (mặc định "failing", chỉ được đổi cờ pass/fail, cấm xóa test), git commit. Mỗi session mới bắt đầu bằng: đọc progress + git log, chạy test end-to-end trước rồi mới làm feature mới. Context là tài nguyên hữu hạn ("context rot"): giữ tập token nhỏ nhất mà đủ tín hiệu; subagent chỉ trả về tóm tắt 1.000–2.000 token.
- Viết tool cho agent như viết giao diện cho người dùng (ACI): ít tool, mỗi tool một mục đích rõ ràng, ưu tiên `search_*` thay vì `list_*`, đặt tên có namespace. Đánh giá bằng eval nhỏ (~20 case) + LLM-as-judge chấm 0.0–1.0 + pass/fail, cộng với kiểm thử bằng tay — vì người test mới phát hiện agent hay chọn nguồn SEO rác thay vì nguồn uy tín.
- Claude Code subagent / Agent SDK: mỗi subagent có context, system prompt, tool và quyền riêng; chỉ trả về tóm tắt; có giới hạn cứng — sâu tối đa 3 tầng, tối đa 20 subagent cùng lúc, giới hạn tiền (`maxBudgetUsd`). Prompt chỉ "khuyên" được model, còn giới hạn phải do harness cưỡng chế.

**Chuyển được sang loop của mình:** giữ tách biệt builder – grader (grader phải hoài nghi, có ví dụ chấm mẫu); taste lock chính là sprint contract (viết ra file, có check quan sát được từng mục); gate chạy trước, dạng JSON, chỉ đổi cờ pass/fail, cấm xóa check hỏng; mọi state nằm ở file (progress + git + gate JSON) để agent chết giữa chừng vẫn resume được — đây là cách sửa lỗi probe-4; fix tối đa 2 lỗi/vòng, dừng ở 3 vòng; worker chỉ trả tóm tắt ngắn + đường dẫn file; người kiểm thử cuối bằng tay trên điện thoại thật.

**Không chuyển được:** con số +90,2% là cho nghiên cứu mở, không phải coding (app mobile các phần phụ thuộc nhau, khó song song); Anthropic đốt 15–20 lần token/tiền ($200 so với $9) còn mình là $0.00 nên không thể "mua" chất lượng bằng thêm agent; các run của họ dài 4–6 giờ, mình chỉ có 5 giờ với tối đa 3 vòng; Agent Teams và Agent SDK là hệ của Anthropic, không dùng được với stack Gemini/Groq + Expo của mình; không được để agent tự sửa prompt của chính nó giữa sprint; và các bài đã đọc **không nói gì về GUARD/chống prompt-injection** — khoảng trống này vẫn chưa có đáp án từ Anthropic.
