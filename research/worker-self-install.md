## 1. Recommendation — the single most optimal self-install approach

### 1.1 The recommendation

**Primary (only) distribution mechanism: the repo itself as a self-contained, vendored, pinned install unit — a non-interactive `install.sh` + a verbatim "For AI agents" paste-prompt in the README + an `AGENTS.md` that is the machine-readable install contract.**

Concretely, the user flow stays exactly as the user described it — drop the repo link into any agent and say "install this kit for yourself" — and the agent executes this deterministic sequence:

1. `git clone https://github.com/phamTuan207/frontend-agent-kit.git` (or `git pull --ff-only` if already cloned).
2. Read `AGENTS.md` (repo root — most hosts auto-read it as project instructions).
3. Run `./install.sh` (extended, see §1.3). The script is non-interactive, detects the host(s) actually installed on the machine, copies vendored skill files into **every** applicable host skills directory, installs the OpenCode command file, installs reference data, backs up same-named pre-existing skills, runs `verify.sh`, and warms the Impeccable engine (best-effort, `--no-warm` fallback). It never downloads code at install time except the single Impeccable engine binary (digest-checked upstream since skill v4.8.0 — see §5.4).
4. Best-effort host-native extras, **inside the same script, failures reported not fatal**: install the Impeccable design hook where the host supports it (`npx impeccable install --providers=<detected> --scope=global`, non-interactive flags); add the Playwright MCP server where the host has an MCP CLI (`claude mcp add`, `codex mcp add`, `gemini mcp add`, `opencode mcp add`). Figma is **excluded** from unattended install — it requires human OAuth and is deferred to the user with an exact command (see §7.7).
5. **Restart / reload the host session**, then re-verify in the new session (skill appears in the host's skill list; bundled smoke checks pass). Report install paths + per-host results + anything unfinished.

Plugin-marketplace manifests (`.claude-plugin/marketplace.json`, `.codex-plugin/plugin.json`) and `npx skills add` are **documented accelerators inside the same repo, not alternatives**: the README lists the one-command plugin install for Claude Code / Codex as the fast path for those two hosts, and `npx skills add <repo-url>` as a convenience — but neither is the primary, because neither covers all seven target hosts.

### 1.2 Why this beats the alternatives (evidence)

| Alternative | Why it loses as the primary |
|---|---|
| **Plugin marketplaces as primary** (Claude `/plugin marketplace add` + Codex `codex plugin …`) | VERIFIED to exist and work well on Claude Code and Codex (official docs, §3.7/§7.1–7.2). But: only Claude Code and Codex have mature plugin systems. OpenCode plugins are a different mechanism; Gemini uses extensions (`gemini extensions install`); Copilot has no equivalent skill-plugin install (it needs `.github/instructions/` files — GSAP README, VERIFIED §3.8); Hermes has no marketplace; Muse (consumer app) has no install at all (§7.7). A plugin-primary kit would leave 4 of 7 hosts with no install path. Plugins also load only at session start or `/reload-plugins`, need `--yes` for scripted installs with a `command` source, and can be installed-but-disabled via `defaultEnabled` — more silent-failure surface than a file copy. |
| **`npx skills add <repo>` as primary** (vercel-labs/skills CLI) | VERIFIED as a real, well-built CLI: 38,719 stars, MIT, supports "OpenCode, Claude Code, Codex, Cursor, and 75 more", auto-detects agents, `-a/-g/-y/--skill` flags, symlink mode + `skills-lock.json` (VERIFIED, README read in full 2026-11-10). But three disqualifiers as primary: (a) **Node.js 22.20+ required** — a hard gate on fresh machines and on any host without a current Node; (b) **host coverage for our exact targets is unverified** — whether `-a` accepts Muse, CommandCode (`cmd`), or Hermes was not established (supported-agents page not opened; see §10); (c) **repo-layout fit is unverified** — the CLI installs skills from a repo, but our kit's skills live in two trees (`skills/` + `vendor/`) with reference data that must land in `~/.local/share/agent-design-references/` and an OpenCode command file in `~/.config/opencode/commands/`; there is no evidence the CLI reproduces that layout. Symlink mode also fails on filesystems without symlink support (Windows without developer mode). It is an excellent accelerator for the hosts it covers, not a universal installer. |
| **Upstream installers as primary** (`npx impeccable install`, `npx ui-ux-pro-max-cli init --ai …`, `npx skills add Leonxlnx/taste-skill`) | Each is VERIFIED current (§4). But they are **interactive pickers**: `npx impeccable install` asks which providers + project/global; `npx skills add` prompts for agents/skills unless fully flagged; taste `install.sh` prompts too. An unattended agent stalls at a prompt it cannot see, or picks wrong defaults. They also fetch `@latest` (unpinned) — version drift by design — and each is a separate command the agent must sequence. They are the right tool for the *hook* step (step 4 above), not for the kit itself. |
| **`curl | bash` / `bash <(curl …)` / `irm | iex` bootstrap** (mpesa, msp-skills offer this) | Fastest for a human, worst for an agent kit. VERIFIED security evidence (§8.8): 59.9% of install scripts have no integrity check; only ~7.6% have checks surviving a compromised host; prompt-injection via a malicious README can make an agent run an attacker's install script. Our kit's own v1 model (vendored, pinned files, no remote code execution at install) is strictly safer, and the repo is public so `git clone` needs no bootstrap script at all. Rejected as primary; do not add one. |

**Why file-copy + install.sh + paste-prompt wins on the three "optimal" criteria:**

- **Fewest steps that still reliably reach 70–80% slop-free:** the user pastes one prompt; the agent runs two commands (`git clone`, `./install.sh`) + a restart. No per-host branching in the user's head, no interactive pickers, no auth. The critique loop (the part that actually delivers "slop-free") is the Impeccable detector + design hook + Playwright eyes — all installed by the same script, deterministically, from vendored files.
- **Widest host compatibility:** file-copy is the *only* mechanism evidenced on all seven targets. `~/.agents/skills/` is the emerging cross-agent standard path (VERIFIED: remote-gpu-trainer table; Gemini CLI docs — `.agents/skills/` alias takes precedence within its tier; OpenCode reads `~/.agents/skills/` globally; Hermes `skills.external_dirs` can point at it; Muse Code reads `~/.agents/skills/`). Host-specific dirs (`~/.claude/skills/`, `~/.config/opencode/skills/`, `~/.codex/skills/` vs `~/.agents/skills/` — see discrepancy §10.2) are covered by copying to *all* applicable dirs, the way `install.sh` already does for Codex/OpenCode. Copilot gets `.github/instructions/` + `.github/copilot-instructions.md` file artifacts (GSAP's own documented pattern, VERIFIED). Muse (consumer app) gets `~/workspace/custom-skills/` copy + a paste-into-chat fallback (see §7.7 — honestly labelled as the weakest host).
- **Cheapest reliable self-critique loop:** the loop is *local and free* — Impeccable's deterministic 62-rule detector binary (no API key, no per-call cost) + taste's headless-Chrome checker + Playwright screenshots. No paid API, no remote MCP server, no per-token cost beyond the agent's own context. The hook (not the skill alone) is what makes the loop *reliable* — it runs automatically instead of only when the agent remembers — which is why step 4 (hook install) is part of the primary flow, not an optional extra.

### 1.3 What the primary approach requires the repo to contain (evolution of v1, not greenfield)

1. **`install.sh` extended, still non-interactive:** host detection (which of `claude`, `codex`, `opencode`, `gemini`, `copilot`, `hermes`, `cmd` binaries/config dirs exist); copy to every applicable skills dir (add `~/.claude/skills/`, `~/.gemini/skills/`, `~/.hermes/skills/`, `~/.codex/skills/` — pending the §10.2 discrepancy resolution — plus Copilot `.github/` artifacts and Muse `~/workspace/custom-skills/` when that path exists); keep the backup behaviour; keep `--no-warm`; add prerequisite checks it currently lacks (`git`, `node` version when needed, `python3` already checked); add a `--hosts=` filter and a `--dry-run` that prints planned actions without writing (msp-skills' `governance.md` pattern, §3.3).
2. **A verbatim "For AI agents" section in README.md** (remote-gpu-trainer pattern, §3.1): a copy-paste prompt the user drops alongside the repo link, naming host detection, clone-or-pull, the script, the restart, the per-host confirmation commands, and the report-back format. The prompt must be written so the agent needs no further instruction.
3. **Plugin manifests as accelerators:** `.claude-plugin/marketplace.json` + `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json` at repo root, so Claude Code / Codex users can one-command install (`/plugin install frontend-agent-kit@<marketplace>`). These must bundle the same vendored skills + hooks, not a second copy of the logic.
4. **Hook + MCP as best-effort script steps:** `npx impeccable install --providers=<detected> --scope=global` (verify the `-y`/non-interactive flag exists — currently CLAIMED from secondary sources, §10.5) and Playwright MCP adds per host CLI. Failures here must not fail the whole install; they are reported as "hook/MCP pending — run X or restart Y".
5. **Version refresh (see §5):** Impeccable 4.5.0 → 4.8.1 (engine 0.1.11 → 0.1.19), Taste v2-experimental → 2.5.1, Pro Max 2.13.0 → 2.15.0. GSAP is already current (upstream HEAD == v1 pin, VERIFIED §5.3). Re-pinning must be a documented, repeatable step (see §5.5), because every upstream in this kit ships new releases monthly.

### 1.4 Trade-offs (explicit)

- **No automatic updates.** A vendored copy goes stale the day an upstream ships (v1 proves it: 5 Impeccable releases behind in ~1 month). Mitigation: `install.sh` re-run after `git pull` is the update path (taste-skill's symlink model does this better — `git pull` updates in place — but symlinks break the backup semantics and Windows support; the trade is deliberate). A `kit update` command / cron reminder belongs in phase 2.
- **No single-command install for 4 of 7 hosts.** Copilot, Hermes, Gemini CLI, and Muse have no one-command plugin install for this kit; they get file copies + a restart. This is slower to *perceive* as installed (the user must trust the report, not a UI badge) — hence the mandatory per-host confirmation commands in the paste-prompt.
- **Hook install still depends on upstream's installer.** If `npx impeccable install` stays interactive or its non-interactive flags change, the hook step degrades to "manual: run this command". The kit still works without the hook (skill invocation is manual), but the critique loop loses its automaticity — the single biggest quality risk. This is why the tie-break experiment (§1.5) matters.
- **Muse (consumer app) is a second-class host.** No permanent install exists (VERIFIED via multiple secondary sources, §7.7); the best the kit offers is a `~/workspace/custom-skills/` copy in this VM's deployment plus paste-into-chat. If the user's real daily driver is the Muse app, the kit's value there is "paste the orchestrator prompt + skill files into a chat", not "installed". State this to the user; do not oversell.
- **Supply-chain surface is the vendored files themselves.** Vendoring removes the `curl|bash` risk but concentrates trust in the pinned commits. Mitigation already available upstream: Impeccable 4.8.0+ checks engine downloads against digests committed alongside the skill (VERIFIED, changelog §5.1); the kit should record a SHA-256 manifest of vendored trees and verify it in `verify.sh` (new step, cheap).

### 1.5 Tie-break experiment (if the two best approaches tie)

The genuine tie is **file-copy primary vs `npx skills add` primary**. Both are one user step (paste a prompt / run one command). The experiment that breaks it — run in phase 2, in clean environments, not speculated here:

> **Clean-env head-to-head:** for each of the 7 target hosts, on a fresh VM/container with only that host installed (plus git; Node 22.20+ installed on half the matrix, absent on the other half), paste the same repo link + one prompt and record, with no human intervention beyond the paste: (a) did all 12 skills land in a directory the host actually reads? (b) did each skill appear in the host's skill list after the documented restart/reload? (c) did `verify.sh` (or its equivalent assertions) pass? (d) did a probe build (vague brief → landing page) run with the Impeccable hook firing at least once without being manually invoked? The approach that passes (a)–(c) on more hosts, and (d) on at least the Claude/Codex/OpenCode subset, becomes primary. **If `npx skills add` passes (a)–(c) on ≥6/7 hosts including Muse/Hermes/Copilot, it displaces file-copy as primary** and `install.sh` becomes the fallback for Node-less machines. Until that experiment runs, file-copy is primary on the evidence above — it is the only approach with *positive* evidence on all seven hosts.

### 2.3 `install.sh` and `verify.sh` — exact behaviour

`install.sh` (verbatim behaviour, read in full):

- Linux-only gate: `uname -s` must be `Linux`, else exit 2. No Windows/macOS path.
- Prerequisite checks: only `cp mv mkdir date python3`. **It does NOT check `git` or `node`** (README says git is needed, but the script never verifies it).
- Backup: same-named existing skills are moved to `~/.local/share/frontend-agent-kit/backups/<UTC timestamp>-$$` before replacement.
- Install method: `cp -a` **copies** (not symlinks): impeccable codex-skill → `~/.agents/skills/impeccable`; impeccable opencode-skill → `~/.config/opencode/skills/impeccable`; command file → `~/.config/opencode/commands/impeccable.md`; 8 GSAP skills → `~/.agents/skills/`; `threeui`, `ui-ux-pro-max-reference`, `taste-reference` → `~/.agents/skills/`; reference data → `~/.local/share/agent-design-references/{ui-ux-pro-max,taste}`.
- Then runs `verify.sh`; then warms the Impeccable engine (`scripts/impeccable engine-probe`, downloads the binary once; `--no-warm` skips; failure is non-fatal with a warning).
- **What it does NOT do:** no `~/.claude/skills` target anywhere; no hooks installed (upstream README says run `npx impeccable install` to get hooks — a plain `cp -a` skips the design hook entirely, so the detector only runs when the agent remembers to invoke it); no MCP servers; no plugin marketplace files (`.claude-plugin/`, `.codex-plugin/`); no Node/git checks; no `--dry-run`.

`verify.sh` (verbatim behaviour, read in full): checks 12 `SKILL.md` paths exist under `~/.agents/skills/` (11) + `~/.config/opencode/skills/impeccable/SKILL.md`, the OpenCode command file, `refs/ui-ux-pro-max/scripts/search.py`, `refs/taste/SKILL.md`; then runs Pro Max `search.py 'editorial portfolio' --domain style` and greps for `Result 1`. Prints `OK: 12 design/reference skills, OpenCode Impeccable command, Pro Max search, Taste reference.`
**What it does NOT check:** whether any agent actually loaded a skill, the Impeccable engine version, Node, a browser/Playwright, hooks, or MCP servers. It proves files exist, not that the kit works. (Not run in this VM — read-only rule, and it checks `$HOME` paths that are empty here, so a run would fail trivially; do not present a run I didn't do.)

### 3.1 remote-gpu-trainer — the best "For AI agents" template seen

- **Source:** https://github.com/Hanyuyuan6/remote-gpu-trainer — README read in full (532 lines), VERIFIED 2026-11-10. 42 stars, MIT, created 2026-06-18.
- **Mechanism:** the README has a dedicated "For AI agents" section with a human prompt to paste:
  > "Install the remote-gpu-trainer agent skill. Read https://raw.githubusercontent.com/Hanyuyuan6/remote-gpu-trainer/main/README.md and follow its 'For AI agents' section for this host. Then tell me where you installed it and how you confirmed it loaded."
- **Agent section, step by step:** (1) **find the skills dir** — a host table (Claude Code `~/.claude/skills/`, Codex/Cursor/Gemini CLI/Copilot `~/.agents/skills/`), env-var host detection (`CLAUDECODE=1`, `GEMINI_CLI=1`), and the note "hosts that share a directory need only one copy" plus "Cloud agents… do not read these local folders"; (2) **idempotent clone-or-pull** block with a `SKILLS_DIR` variable, folder name must match the skill `name`, a non-git fallback via `main.tar.gz` download, "ask the user before replacing" a non-empty non-git folder, "do not edit the installed copy"; (3) **confirm loaded** — a bundled Python eval (`evals/run_evals.py`) must exit 0 printing `N/N cases reachable`, then per-host checks (Claude Code `/skills`, `/reload-skills` if the dir didn't exist at session start; Codex `$`/`/skills`, restart if missing; Gemini `/skills list`, `/skills reload`; VS Code `/skills`); report install path + `git rev-parse --short HEAD`.
- **What it proves:** a README can carry a complete, host-aware, idempotent, self-verifying install contract in one paste-prompt. This is the template our README's "For AI agents" section should copy structurally. Its weak point (for us): it installs exactly one skill into one dir; our kit needs 12 skills + reference data + a command file + hooks/MCP, so the pattern needs scaling, not just copying.
- **Note:** its host table says Codex uses `~/.agents/skills/` — which conflicts with the GSAP README's `~/.codex/skills/` for Codex (see §3.8 and discrepancy §10.2).

## 6. The minimal self-install contract

The smallest set of capabilities an agent must have for self-install to work at all. If any step is missing, self-install fails or degrades to a human task — the contract names the fallback for each.

| # | Step | What it requires of the agent/host | If missing |
|---|---|---|---|
| 1 | **Read the repo** — fetch `README.md` + `AGENTS.md` from the link (raw GitHub URL or clone) | Network read access to github.com / raw.githubusercontent.com; ability to read files | Cannot start. Fallback: user pastes the files into chat (Muse paste-model, §7.7). |
| 2 | **Clone (or pull) the repo** | `git` installed; network egress to github.com; write access to a working directory | Fallback: tarball download (`main.tar.gz`) — remote-gpu-trainer documents this; or the user clones and points the agent at the local path. |
| 3 | **Detect the host** | Ability to inspect its own environment (env vars `CLAUDECODE`, `GEMINI_CLI`; which binaries/config dirs exist: `~/.claude/`, `~/.codex/`, `~/.config/opencode/`, `~/.gemini/`, `~/.hermes/`) | Agent installs to the wrong dir or all dirs (wasteful but harmless if it copies to every known dir — the v1 `install.sh` approach of copying to all applicable dirs is the robust default when detection fails). |
| 4 | **Copy files to skills dirs** (the core step) | Shell (`bash`/`sh`) or file-write tools; write access to `$HOME` paths **outside** the project dir (the #1 sandbox failure, §8.1) | Degrades to "Path B" (msp-skills): the agent prints exact human commands and the user runs them. A project-local install (`.agents/skills/` in the repo) is a partial fallback — skills work in that project only. |
| 5 | **Run a script** (`./install.sh`, engine warm, smoke tests) | Shell execution permission; network for the one engine download (or `--no-warm` deferral) | Manual copy of files per the README table; engine downloads on first use. |

## 8. Failure modes (documented evidence where possible; speculation labelled)

### 8.1 Sandbox / approvals block the install itself

- **Codex default sandbox (`workspace-write`):** OS-enforced (Seatbelt macOS, bubblewrap+seccomp Linux), network OFF, writes confined to workspace + /tmp, `.git`/`.codex` read-only; escaping needs per-command human approval (`approval_policy` `on-request` default; `never` = blocked commands just fail); `danger-full-access` / `--dangerously-bypass-approvals-and-sandbox` removes all protection; trusted-repo `.codex/config.toml` can switch approvals off; **MCP servers run on the host, outside the sandbox.** (VERIFIED, OpenAI Codex docs — from pre-compaction research, accessed 2026-11-10.) Every `npx` / `git clone` / `curl` install step needs approval or fails. The paste-prompt must tell the user to expect approval prompts, and `install.sh` must be runnable as a single approved command rather than dozens of individually-approved steps.
- **Claude Code permission modes** likewise gate shell/config edits (CLAIMED — standard behaviour; exact mode names not re-verified this session).
- **Gemini CLI skill activation** requires a UI consent prompt per skill (VERIFIED, §7 table) — install can succeed while activation stalls on an unanswered prompt.

### 8.2 The restart / reload boundary — the #1 false-failure mode

Skills, MCP servers, and plugins load at process/session start almost everywhere: Claude Code (new top-level skills dir → `/reload-skills` or restart; MCP config edit → restart or `/mcp` reconnect), Codex (new plugin → `/new` session; MCP → restart), OpenCode (restart), Gemini CLI (restart after settings.json; `/skills reload` for skills), Claude Desktop (fully quit + reopen), VS Code/Cursor (reload window), Trae (restart after copy). An install that "succeeds" in the same session the agent then tests in will look broken. **The install contract must include an explicit restart step + a re-verification in the NEW session** (§6, step 7). Every "skill not found" report that arrives without a restart having happened is suspect until the restart is done.

### 8.3 Interactive installers block unattended agents

`npx impeccable install` asks which providers + project/global; `npx skills add` prompts for agents/skills if not fully flagged (needs `-a … -y --skill …`); taste `install.sh` prompts too. An agent that just runs the bare command stalls waiting for input it cannot see, or picks wrong defaults. **Rule for the kit: every command in the paste-prompt and in `install.sh` must be fully flagged / non-interactive, or the prompt must say exactly what to answer.** The `-y` flag for `npx impeccable install` is CLAIMED (secondary sources) — verify before relying on it (§10.5).

### 8.4 Silent config-format failures (wrong key, no error, server never appears)

- Codex: `[mcpServers.x]` / `[mcp.servers.x]` instead of `[mcp_servers.x]` (TOML).
- Copilot: `mcpServers` instead of `servers` in `.vscode/mcp.json`.
- OpenCode: v1 `mcp.<name>` + `enabled` vs v2 `mcp.servers.<name>` + `disabled` (VERIFIED — official v2 docs §7; third-party guides still show v1).
- Gemini: `url` vs `httpUrl` (streamable HTTP) vs Antigravity `serverUrl`.
- Figma: project-scope default vs `--scope user` for global (Claude); a project-scoped Figma server silently "missing" in other projects is a scope mistake, not an install failure.
**Mitigation:** `install.sh` should prefer host CLIs (`claude mcp add`, `codex mcp add`, `gemini mcp add`, `opencode mcp add`) over hand-editing JSON/TOML — the CLI writes the correct schema. Hand-edited configs need a verification step (`<host> mcp list`) in the same session.

### 8.5 Skill never fires (discovery failure, not install failure)

- Vague `description` frontmatter — the `description` is the only thing the agent sees at discovery (agentskills.io progressive disclosure: startup loads only name+description; full SKILL.md loads on task match; references load on demand — VERIFIED, agentskills.io read in full 2026-11-10). A skill with a weak description is installed but invisible.
- Wrong path (`SKILL.md` not at the skill-folder root), double-nested folder from a bad clone/copy, name/folder mismatch (spec requires the `name` field to match the parent directory name; `name` 1–64 chars, lowercase alphanumerics + hyphens, no leading/trailing/double hyphen; `description` 1–1024 chars; spec defines 6 frontmatter fields: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`; SKILL.md recommended <500 lines / <5000 tokens; validator `skills-ref validate` — VERIFIED, agentskills.io + secondary spec sources, 2026-11-10).
- Reserved name colliding with a built-in command (e.g. a skill named `resume` kills Claude Code's built-in `/resume`).
- Project-level skill shadowing the global one; `user-invocable: false`.
- **Our kit's specific instance:** the `taste-reference` / `ui-ux-pro-max-reference` descriptions gate on "only when the user explicitly asks" (§2.5) — by design they will not fire on a vague brief. The orchestrator must invoke them explicitly.

### 8.6 Missing runtimes

Node version matrix (VERIFIED where stated): skills CLI needs **22.20+**; taste scripts need Node 22+; impeccable npx CLI needs 22.18+ (pinned) / **18.19+ (current, since v4.6.0)**; Playwright MCP needs Node 18+ (one source says 20+ — discrepancy §10.6); Gemini extension install needs nothing but the CLI. Chrome/Edge/Chromium required for the taste checker + impeccable `detect <url>`; `npx playwright install-deps` needed on Linux; `uv` needed for `uvx`-based MCP servers; `git` needed for clone-based installs (absent on fresh Windows without Git for Windows — msp-skills notes `irm|iex` bootstrap.ps1 as the no-git path). **V1's `install.sh` checks none of `git`/`node`/`chrome`** — a fresh-machine install can fail with a confusing error from deep inside a later step instead of a clear prerequisite message at the top.

### 8.7 Network

Sandbox blocks egress (§8.1); corporate proxies; `npx`/`npm`/`git` need network at install time; taste photo/icon fetching needs network (bundled photos work offline); first-run engine download (Impeccable) needs network or `--no-warm`/deferred. **Design consequence: the kit's install must need network exactly twice — `git clone` and the one engine download — and degrade gracefully (`--no-warm`) when the second is unavailable.** Anything that re-downloads per skill or per host multiplies the failure surface.

### 8.8 Security / supply chain (evidence, not speculation)

- `curl|bash`, `bash <(curl …)`, `irm|iex`, `npx <unpinned>@latest` all execute remote code as the user with no integrity check. Evidence: KTH agentic supply-chain paper (2026-06-25) — prompt injection via a malicious README/docs can make an agent run an attacker's install script; the agent runs under developer credentials. Medium install-script study (2026-10-21, 2,182 unique install URLs): 59.9% have no integrity check; only ~7.6% have checks surviving a compromised host (embedded hash/signature); 54% don't guard against truncated downloads. markdownregistry audit (data frozen 2026-09-27; 61,170 SKILL.md files): 174 (0.3%) fail a critical check, 395 contain curl/wget piped to shell; Anthropic guidance: use skills only from trusted sources, audit others thoroughly (check for download-and-run commands, credential reads `~/.ssh`/`~/.aws`/`.env`, hidden text). (All CLAIMED via the cited studies as summarised in pre-compaction research, accessed 2026-11-10 — the underlying papers were not re-opened this session; treat the numbers as CLAIMED, the direction as well-evidenced.)
- **Inside the kit's own dependency:** Impeccable live-mode Apply runs CLIs with sandbox bypass (`--dangerously-bypass-approvals-and-sandbox` / `--permission-mode bypassPermissions`, environment inherited — VERIFIED, upstream README §3.7). Any kit doc describing live mode must flag this.
- **"Slopsquatting"** (hallucinated package names registered by attackers) and npm postinstall hooks are adjacent risks for any `@latest` install.
- **Implication for the recommendation (§1):** prefer vendored, pinned, hash-checkable files in the repo (v1's model) over `curl|bash`/`@latest`; never put secrets in config files (use env-var names — Codex `--env` values land in plaintext in config.toml, VERIFIED §7); add a SHA-256 manifest of vendored trees verified by `verify.sh`.

### 8.9 Version drift / stale commands (demonstrated, not hypothetical)

Figma stdio → remote HTTP (§4); img2threejs MCP form never existed (§4); taste v2 → 2.5.1 rebuild (§5.2); Impeccable 4.5.0 → 4.8.1 (§5.1); Gemini CLI → Antigravity migration 2026-06-18 (CLAIMED, §10.3); OpenCode v1 → v2 config schema change (§7). **Any hardcoded command in the kit needs a version-pinning + re-verification policy (§5.5), and the paste-prompt must tell the agent to check the upstream README when a command fails rather than improvising a replacement.**

### 8.10 Cloud / web agents can't self-install locally

remote-gpu-trainer README (VERIFIED §3.1): cloud sessions (Claude Code cloud, Cursor Cloud Agents) do not read local skill folders. msp-skills FAQ (VERIFIED §3.3): ChatGPT web / Claude.ai web / Microsoft 365 Copilot need a remote HTTP MCP server, which a local-files kit cannot provide. **A user who drops the repo link into a web chat gets a chat-mode skill at best (§3.5 caveat), not an install.** The paste-prompt should say which host it is running on and refuse gracefully (with the paste-model fallback) when it is a cloud session.

### 8.11 Agent Skills open standard — the format all of this rests on

VERIFIED (https://agentskills.io read in full, 2026-11-10): "A skill is a folder containing a `SKILL.md` file… metadata (`name` and `description`, at minimum) and instructions… Skills can also bundle scripts, reference materials, templates." Layout: `SKILL.md` (required), `scripts/`, `references/`, `assets/` (optional). Progressive disclosure in 3 stages: (1) Discovery — startup loads only name+description; (2) Activation — task match loads full SKILL.md; (3) Execution — follow instructions, run bundled code / load references as needed. Format originally developed by Anthropic, released as an open standard; Anthropic donated the standard to the Agentic AI Foundation (Linux Foundation) on 2026-10-22, format unchanged (CLAIMED, secondary sources); 40+ supporting tools; Claude Code also accepts extra fields (`disable-model-invocation`, `paths`, `when_to_use`); uploads to claude.ai/Claude API reject frontmatter fields outside the six. **Why this matters for the kit:** the standard is the reason one vendored tree can serve seven hosts — the kit's job is purely to put the right folders in the right directories per host, not to rewrite skills per host. The only per-host artefacts are the thin wrappers v1 already ships (codex vs opencode Impeccable variants differ only in frontmatter + paths, §2.4) and the Copilot instructions files (§3.8).

3. **Bundled checks pass:** `verify.sh` exits 0 (or its per-host equivalent assertions); Pro Max `search.py` smoke test returns `Result 1`; `impeccable engine-probe` (or `detect --version`) reports engine ≥0.1.19 after re-pin.
4. **Hook present where supported:** `hooks status` (Claude) / `/hooks` approval state (Codex) / `hermes plugins enable` state shows the Impeccable design hook wired; on hosts without hook support, the report says so explicitly rather than silently omitting it.
5. **MCP present where configured:** Playwright appears in `<host> mcp list` / `/mcp` and connects; Figma is explicitly NOT installed (human-OAuth pending) and the report names the exact command for the user.
6. **Probe build (the 70–80% test):** from a vague brief ("landing page for a language-learning app, ref like Apple/Anthropic" — the user's canonical example), the agent produces a page; record whether the Impeccable hook/detector fired at least once without manual invocation, whether Pro Max or Taste was consulted before building, and whether a Playwright screenshot was taken and reviewed. Score the output against the kit's own Definition of Done (to be set by the council — this spec does not invent the rubric).
7. **Failure behaviour:** if any step fails, the agent's report names the failed step, the error, and the exact human action needed — no silent skip, no invented fix (council rule 1).

### 9.3 Pass / fail criteria

- **Per-host PASS:** assertions 1–3 pass; 4–5 pass or are explicitly reported as unsupported/pending with the exact follow-up command; 6 completes with the hook firing at least once on hook-supported hosts; 7 holds on any failure.
- **Kit PASS:** per-host PASS on Claude Code, Codex, and OpenCode (the v1 hosts + Claude), plus at least 2 of the remaining 4 hosts. **Kit FAIL otherwise, or if any host silently reports success while assertion 2 fails** (the false-success mode §8.2 exists to catch).
- **Tie-break readout (§1.5):** compare variant A vs B per host on assertions 1–3 and on the count of human interventions. If B passes 1–3 on ≥6/7 hosts including Muse/Hermes/Copilot, B becomes primary.

### 9.4 What this spec deliberately does NOT test

No performance benchmarks, no design-quality judging beyond assertion 6's process checks (quality judging belongs to the council/red team with its own rubric), no Windows/macOS paths until `install.sh` gains them (v1 is Linux-only — the test matrix is Linux until the script changes).
